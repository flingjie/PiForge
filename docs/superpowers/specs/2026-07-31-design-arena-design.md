# Design Arena — Architecture Decision Engine

Date: 2026-07-31

## Context

Current AI Coding Agents follow a linear pipeline: User → Planner → Execution → SubAgent. This produces a single design, missing the core insight that the best software designs emerge from multi-perspective competition, not single-pass generation.

Design Arena upgrades this to: **Plan → Debate → Validate → Execute**, where Debate explores the design space through structured multi-agent competition and Validate verifies assumptions before code is written.

## Architecture Overview

```
User → Requirement → Planner → Plan
                                │
┌───────────────────────────────┘
│  Design Arena
│
│  Gap Detector ──→ Sub-Problem Battles (recursive)
│                      │
│    ┌─────────────────┼─────────────────┐
│    ▼                 ▼                 ▼
│  Solution A      Solution B      Solution C
│  (speed)         (maintain)      (minimal)
│    │                 │                 │
│    └─────────────────┼─────────────────┘
│                      ▼
│                   Critic
│                      │
│                      ▼
│              Need More Debate?
│               YES → Expand → Battle Again
│               NO  → Synthesizer
│                      │
│                   ┌──┴──┐
│                   ▼     ▼
│                Plan   TODO Graph
│               (修订)  (执行图)
│                      │
│                      ▼
│               Static Validation
│
└───────────────────────────────┘
                                │
                                ▼
                       Orchestrator
                                │
                        Subagent Executors
```

## Key Design Decisions

### 1. Entry Point: Plan

Arena receives the Planner's output (Plan), not raw requirements. It challenges and refines existing decisions rather than generating design from scratch.

### 2. Battle Scope: High-Uncertainty Only

Gap Detector scans the Plan and identifies sub-problems worth battling. Criteria:
- **Cross-module boundaries**: interfaces spanning packages or services
- **Tech selection**: database, message queue, framework choices
- **Critical path impact**: decisions significantly affecting performance, security, or maintainability

Only flagged sub-problems enter the Arena. Low-risk decisions in the Plan pass through unchanged.

### 3. Solution Agents: Core 3 + Typed Extensions

**Core (always dispatched):**
| Agent | Persona |
|-------|---------|
| speed | Fastest implementation, minimal abstraction, low cost |
| maintain | Long-term maintenance, modularity, dependency injection |
| minimal | YAGNI extremist, delete more than add |

**Extensions (dispatched by sub-problem type):**
| Sub-Problem Type | +Agents |
|------------------|---------|
| Tech selection (DB/MQ/Cache) | perf |
| Security boundary (Auth/Authz/Data) | secure |
| Cross-module interface | scalable |
| Data processing / high throughput | perf, secure |
| Concurrency / distributed | perf, scalable |

### 4. Critic: Skeptical Adversary

Critic does not propose solutions. It only finds weaknesses. Prompt: "Assume every design is wrong. Find weaknesses."

### 5. Gap Detector & Recursive Battles

Gap Detector identifies insufficiently debated sub-problems and triggers recursive battles. The battle tree mirrors the problem decomposition:

```
Architecture
├── API Battle
├── DB Battle
├── Queue Battle
│   ├── Kafka
│   ├── Rabbit
│   └── NATS
├── Cache Battle
└── Monitoring Battle
```

### 6. Synthesizer: Fusion, Not Voting

Synthesizer does not pick a winner. It fuses the best parts of each solution:
- Adopt Solution B for API design (best maintainability)
- Adopt Solution A for caching (simplest, good enough)
- Adopt Solution C for queueing (best scalability)

Output: revised Plan + TODO Graph (two separate files).

### 7. Static Validation Only

Validation is structural, not runtime:
- Module references resolve correctly
- Interfaces are consistent across packages
- Dependency graph is acyclic

No running code, no benchmarks. Keeps the gate lightweight.

### 8. Plan & TODO Graph: Separate Files

Plan = design decisions ("what + why"). TODO Graph = execution plan ("how + who + dependencies + status"). Both generated by Synthesizer, stored in the same feature directory:

```
.claude/arena/<feature>/
  plan.md
  todo.md
```

### 9. TODO Graph Format

Table + ASCII dependency diagram:

```markdown
## Node Table
| ID | Name | Files | Verify | DependsOn | Status |
|----|------|-------|--------|-----------|--------|

## Dependency Diagram
[1] → [2] [3] → [4]

## Concurrent Groups
G1: [1]
G2: [2, 3]
G3: [4]
```

### 10. Evaluation Rubric

Dimensions are defined in Constitution (stable across battles). Weights are set in Plan with Constitution defaults as fallback:

| Dimension | Default Weight |
|-----------|---------------|
| Decoupling | 20 |
| Maintainability | 20 |
| Extensibility | 15 |
| Testability | 15 |
| Performance | 10 |
| Observability | 10 |
| Implementation complexity | 5 |
| AI Coding Friendliness | 5 |

### 11. Constitution: Self-Evolving, Human-Gated

- Arena may propose Constitution amendments after any battle
- Amendments written to `constitution-proposals.md`
- Human review and approval required before taking effect
- Prevents principle drift from autonomous AI decisions

### 12. Orchestrator Execution Model

- Reads `todo.md`, parses dependency graph
- Dispatches concurrent groups sequentially (G1 → G2 → G3)
- Within a group: nodes run in parallel via subagents
- All Status writes are done by Orchestrator only (single-writer, no conflicts)
- Subagents have no knowledge of the task system

### 13. Failure Handling

- Node fails → retry up to 3 times (with error feedback)
- 3 failures → marked `failed`
- Same-group siblings continue unaffected
- Downstream nodes whose DependsOn includes a failed node → marked `skipped`
- Final report: "N completed, M failed, K skipped"

## File Layout

```
.claude/
  arena/
    constitution.md          # Design constitution (shared across all battles)
    <feature>/
      plan.md                # Design decisions
      todo.md                # Execution graph
    <feature-with-sub-battle>/
      plan.md
      todo.md
      <sub-problem>/
        plan.md
        todo.md
```

## Out of Scope

- Runtime prototype generation and benchmark execution
- Knowledge Replay (historical ADR retrieval)
- Design Evolution Loop (post-implementation feedback)
- Automatic Constitution amendment (proposals only, human-gated)
- Multi-project / cross-repo battles
